# Bitrix24 Idea Factory (конвейер ≤5 часов на 1 приложение)

## Ограничения (обязательные)
- Приложения: **публичные** для **Bitrix24 Marketplace**
- Платформа: **только облако Bitrix24** (не коробочные/онпрем‑специфичные возможности)
- Домены: **CRM**, **Задачи/Проекты**, **Аналитика/Отчёты**, **Чаты**
- Исключить: **внешние интеграции**, **отраслевые решения**
- Язык артефактов: **русский**
- Метод генерации идей: см. `docs/idea-briefs/IDEA_METHOD.md` (**сначала работа/ритуал роли, потом API**; почасовой поток выключен)
- Почасовая автогенерация пятёрок **не запускать**, пока пользователь явно не включит заново

## Выходные артефакты (что создавать в репозитории)
Папка: `docs/idea-briefs/`

### Индекс
- Всегда создавать/обновлять: `docs/idea-briefs/INDEX.md`

### Пакет по одной идее
Для каждой выбранной идеи `NN` (01, 02, …) создавать 4 файла:
- `docs/idea-briefs/NN_<slug>.md`
- `docs/idea-briefs/NN_<slug>__competitors.md`
- `docs/idea-briefs/NN_<slug>__mvp_release_market.md`
- `docs/idea-briefs/NN_<slug>__screens_security_faq.md`

`<slug>` должен быть кратким и стабильным (латиница + подчёркивания), описывать суть.

### Журнал предложений / беклог
- `PROPOSED.md` — сквозная нумерация всех предложений
- `BACKLOG.md` — выбранные идеи (`в беклог N`)
- `IDEA_METHOD.md` — метод и анти‑паттерны

## Конвейер (строго по шагам)

### Шаг 0 — Подготовка (10 минут)
Сформировать 1 предложение:
**“Для кого + где в Bitrix24 боль + какой измеримый эффект”**.

### Шаг 1 — Генерация идей (сначала работа, потом API)
1. Следовать `IDEA_METHOD.md`: роль + ритуал → job → «как сейчас в B24» → клин приложения → короткий взгляд на Маркет/штатив → только потом API/placement.
2. По умолчанию **1–2 идеи**, не 5. Пятёрку — только по явной просьбе и только если это 5 разных работ.
3. Для каждой идеи зафиксировать минимум:
   - сцена/ритуал, ICP
   - боль и цена
   - что делает (работа, не лог)
   - как сейчас обходят в B24
   - чем НЕ штатный B24 / не робот / не фильтр / не типовой отчёт
   - MVP, риски, скоринг
   - placement / API как опора (в конце)

4. Перед сохранением — **чек‑лист дифференциации** (ниже) + анти‑паттерны «мельницы детекторов» из `IDEA_METHOD.md`. Провал = выкинуть.

Сразу отсеивать внешние интеграции и отраслевую специфику.

### Язык для человека (обязательно)
- Первая строка: **сцена + кому больно и чем дорого**.
- **Название** — обычный русский, без жаргона и аббревиатур.
- Порядок в чате: название → боль/цена → что делает → для кого → эффект → MVP → чем не штатный облачный B24 (и не робот/БП) → как сейчас обходят → риски/скоринг → `в беклог N`.
- Детектор/радар: **макс. 1** на пачку (лучше 0). Не добивать пачку вариациями «серия правок / path / fingerprint».
- Лучше **1 сильная**, чем 5 средних.

### Вне IT‑пузыря (обязательно, см. `IDEA_METHOD.md`)
- ICP по умолчанию: **продажи, маркетинг, аккаунт, поддержка, РОП/комдир** — не «тимлид разработки / продуктивность IT».
- Не плодить приложения про WIP, оценки часов, теплокарты дедлайнов, DoR/приёмку задач «как в скраме» — ими завалены сторы, аудитория узкая.
- В пятёрке ≥**3** идеи для не‑IT ролей; ≤**1** про внутреннюю продуктивность задач, и только с явной денежной/клиентской ценой.
- «Идея из жизни» (маркетинг, контент для продаж, разрыв маркетинг↔продажи) — ок; **внешние** каналы (Reddit, рекламные кабинеты и т.п.) — **нет** (ограничение Маркета/репо).

### Чек‑лист дифференциации (обязательный, все пункты)

Идея **дисквалифицируется**, если хотя бы один ответ «да»:

1. Это закрывается **роботом/триггером/БП CRM** 1:1? (смена стадии или условие по полю → создать дело/уведомление/задачу/заполнить поле)
2. Это штатный **контроль дубликатов** лидов/контактов/компаний?
3. Это обычный **отчёт со сравнением периодов / KPI‑панель** без новой *работы* в ритуале?
4. Это **аудит пустого поля** → список → алерт без действия в карточке?
5. Это **«нет следующего дела»** / ещё один дайджест просрочек?
6. Это **искусственный UX поверх чатов** («подтверди приём», «кнопка принял чат»)?
7. Time‑to‑value > 10 минут или нужны широкие права на чтение текста сообщений?
8. Это боль **IT‑продуктивности** (WIP, оценки часов, теплокарта дедлайнов, скрам‑приёмка) без покупателя вне IT?
9. Это **мельница детекторов**: серия правок поля / path / fingerprint / «источник × метрика» / коллизия графа без ясного ритуала «что сделают за 30 секунд»?
10. Платёжный тест провален: идею не объяснить одной фразой без аналитического жаргона?

Если похоже на штатив, но есть ясный зазор — написать зазор явно. Иначе отклонить.

Уроки: **114, 115, 117, 118**; волна штатива **269–273**; робот/БП **285/286/288**; вырождение радаров **274–313**.

### Шаг 2 — Скоринг, реализуемость и техсложность (20 минут)
Оценка 1–5 (3–5 минут на идею), выбрать **Top‑5**.

**A — рынок/ценность**
- частота боли
- платёжность/ROI
- дифференциация (**штраф 1–2 балла**, если слабо отличается от штатного B24)

**B — реализуемость (feasibility)**
- опора на стандартные объекты (CRM/Tasks/IM)
- понятный источник данных
- минимальные права
- без сложной инфраструктуры

**C — техсложность (MVP ≤1–2 недели)**
- UI: 1 killer‑экран + 1–2 настройки
- минимум тяжёлых фоновых процессов
- производительность на больших порталах
- управляемые edge‑cases

**Красные флаги (дисквалификация)**
- постоянный realtime/стриминг/сложные боты в чате
- “админ‑всё” без ясной ценности
- тяжёлая инфраструктура/очереди/внешние хранилища
- нельзя обеспечить time‑to‑value ≤ 10 минут
- копия штатных роботов / дубликатов / типовых отчётов B24

### Шаг 3 — Анализ конкурентов (70 минут)
Для каждой из Top‑5:
- найти 5–10 конкурентов в Marketplace по 10–15 ключевым запросам (синонимы и смежные формулировки)
- **отдельно проверить штатный функционал Bitrix24** (роботы, дубли, отчёты, SLA, задачи)
- собрать по каждому: обещание, механика, installs/оценка (если видны), отзывы (сигналы болей), запрашиваемые права, пробелы
- итог: топ слабых мест рынка + “что мы делаем лучше **и чем не дублируем коробку**”

Записать результат в `__competitors.md`.

### Шаг 4 — УТП + MVP + релиз + текст Маркета (75 минут)
Сформировать:
- **УТП** (1 предложение) — с явным отличием от штатного B24, если уместно
- **MVP 3–5 фич** (строго)
- **Не‑MVP** (что выкидываем, чтобы не распухло)
- план релиза **Неделя 1 / Неделя 2**
- метрики успеха + риски/смягчения
- черновик текста для Маркета: заголовок, подзаголовок, буллеты ценности, quick start, короткий FAQ

Записать в `__mvp_release_market.md`.

### Шаг 5 — Скриншоты + безопасность/модерация + FAQ (70 минут)
Сформировать:
- план 6–8 скриншотов (что на каждом показываем)
- стратегия минимальных прав
- что приложение **не читает/не хранит** (особенно контент сообщений)
- политика хранения (только агрегаты/timestamps)
- производительность (периоды по умолчанию, кэширование)
- FAQ (готовый текст “вставить в Маркет”)

Записать в `__screens_security_faq.md`.

## Правила качества (обязательные)
- Не делать “комбайны” из 8 вкладок в MVP: один главный экран + короткие настройки.
- Побеждать доверием: минимальные права + прозрачное описание безопасности.
- Всегда обеспечивать быстрый старт: **польза ≤ 10 минут после установки**.
- Не предлагать идеи, которые пользователь справедливо отшибает фразой «это же стандартный Bitrix24».

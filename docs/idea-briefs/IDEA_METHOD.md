# Метод генерации идей: от API Bitrix24

Цель — искать идеи от **возможностей облачного Bitrix24** и сразу отсекать копии штатного функционала.

Платформа: **только облако**. Не опираться на коробочные/онпрем‑особые модули.

## Критерий силы идеи
Идея сильная, если за 10 секунд ясно:
1. кому больно;
2. чем дорого (время, деньги, сорванные сделки);
3. почему это **не** закрывается штатным облачным B24.

## Вне IT‑пузыря (обязательный фильтр аудитории)

Покупатель Маркета — чаще **продажи, маркетинг, аккаунтинг, поддержка, операционка**, а не тимлид разработки.

**Искажение, которого избегать:** авторы идей сами из IT и тащат в продукт свои боли про «продуктивность» (WIP‑лимиты, тепловые карты дедлайнов, точность оценок часов, DoR/чеклисты приёмки, «кто двигает сроки в команде разработки»). Таким завалены сторы; узкая аудитория платит мало и редко.

**Искать боли из реальной жизни ролей в B24:**
- маркетинг ↔ продажи (качество лидов, обратная связь по слитым лидам, источники → встречи/деньги);
- менеджер продаж / аккаунт (что сказать клиенту, состав КП, допродажа, прогноз без «айтишного» коучинга процессов);
- контент для продаж внутри CRM (шаблоны по стадии/товару, фиксация обещаний клиенту — **без** внешних соцсетей);
- руководитель продаж (деньги, клиенты, воронка) — не «дисциплина исполнителей задач» как в IT‑скраме.

**В пятёрке:** минимум **3 из 5** идей с ICP = маркетинг / продажи / аккаунт / поддержка / РОП‑комдир.  
Максимум **1 из 5** — «внутренняя продуктивность команды задач», и только если боль денежная/клиентская, не «удобнее жить разработчику».

**Всё ещё запрещено:** внешние интеграции (Reddit, рекламные кабинеты, почтовые сервисы и т.п.) и отраслевые вертикали — боль «из жизни» должна закрываться **объектами облачного B24**.

## Конвейер (каждый час / по запросу «ещё 5»)

1. Прочитать этот файл + `PROPOSED.md`, `BACKLOG.md`, пул идей.
2. Выбрать **1–2 API‑угла** из ротации (не повторять углы последних 5 запусков; блок `## Ротация углов` в `PROPOSED.md`).
3. Сгенерировать кандидатов → прогнать **чек‑лист дифференциации** из skill → оставить 5 живых.
4. Для каждой записать полный формат + поле **«Чем НЕ штатный B24»**.
5. Обновить `PROPOSED.md` и ротацию; закоммитить/запушить в `master`, если поток так настроен.

## Формат идеи (обязательно)

**Для пользователя (в чате) — в таком порядке:**
1. Понятное название на русском (без аббревиатур и англицизмов)
2. Боль
3. Что делает приложение (1–2 фразы)
4. Для кого
5. Эффект
6. MVP
7. Чем НЕ штатный B24
8. Риски, скоринг, `в беклог N`

**В файле дополнительно:** домен, API‑угол, Placement, Механика (техническое, не вместо сути).

Плохие названия: «WIP по department», «Fingerprint closers», «Thrashing стадий», «Live‑коридор P90».  
Хорошие: «Какая задача тормозит весь проект», «Сделки, которые прыгают по стадиям», «Чем сильные менеджеры отличаются по звонкам и встречам».

## Ротация API‑углов

| Код | Угол | Примеры API / точек | Какие идеи искать |
|-----|------|---------------------|-------------------|
| A | События | `event.bind`, ONCRM*, OnTask* | реакция в момент изменения, журналы, **не** тупой «создать дело» = робот |
| B | История стадий/статусов | `crm.stagehistory`, task history | графы, проскоки, thrashing, переносы, SLA‑в‑стадии |
| C | Связи сущностей | deal↔contact↔company↔activity↔task | разрывы цепочек, связанные риски |
| D | Агрегаты | `*.list` + периоды | cohort/fingerprint/распределения — **не** «KPI за неделю vs неделю» как единственная суть |
| E | Оргструктура | user, department | маршрутизация по ролям/отделам |
| F | UI placements | CRM_*/TASK_* | killer‑действие в карточке |
| G | IM‑метаданные | timestamps, participants | очереди/SLA **без текста**; без фейковых «кнопок принял» |
| H | Чеклисты и время | checklist, elapseditem | DoR, пережог часов, приёмка |
| I | Дубли и поиск | crm.duplicate | только если даёт **зазор** vs штатный дедуп (иначе запрещено) |
| J | Товарные строки | product rows | аномалии состава/чека в контексте стадии |

## Разнообразие механик в одной пятёрке (обязательно)

В любых 5 идеях **нельзя**, чтобы 4+ были одного типа «найти проблему → список → алерт».

В пятёрке должно быть минимум **3 разных типа механики** из:
1. **Детектор/радар** — найти аномалию (макс. 2 из 5)
2. **Действие в карточке** — кнопка/мастер, который что‑то создаёт или упрощает работу
3. **Сравнение/коучинг** — профили, эталоны, «чем отличаются сильные»
4. **Помощник решения** — подсказать кому передать, что сделать дальше, как разбить работу
5. **Сводка смысла** — один экран «почему горит», а не сырой список нарушений

Если черновик пятёрки снова весь про «найти X без Y» — переписать до отправки пользователю.

- Робот 1:1: смена стадии → создать дело/задачу/уведомление
- Штатный контроль дубликатов при создании лида/контакта/компании
- «Пустое поле → список → алерт» без истории/события/placement‑действия
- «Нет следующего дела» / ещё один дайджест просрочек
- «KPI/конверсия за период vs период» без новой механики (cohort, fingerprint, граф, распределение)
- Искусственный chat UX: «подтверди приём чата», «кнопка принял handoff» поверх обычного IM
- Чтение/хранение текста сообщений

Отклонённые примеры: **114, 115, 117, 118**.

## Что считается хорошим зазором

- Использует **историю** или **граф** (не один статус «сейчас»)
- Использует **связи** нескольких сущностей
- Делает **placement‑действие**, которого нет в коробке
- Даёт **операционный сигнал в момент события**, но не дублирует роботов (например, детект аномалии, а не создание дела)
- Считает **неочевидную метрику** (P90 в стадии, fingerprint активностей топ‑closers, thrashing стадий)

## Красные флаги реализации

- Нет внешних интеграций и отраслевых решений
- Нет тяжёлого realtime/сложных ботов в MVP
- Time‑to‑value ≤ 10 минут
- Минимальные права

# Метод генерации идей Bitrix24 Marketplace

Платформа: **только облако**. Без внешних интеграций и отраслевых вертикалей.

## Почему старый метод сломался (2026-09-22)

Почасовой поток «от API‑углов → 5 идей» выродился в комбинаторику:

- детекторы серий (правки скидки / владельца / стадий / строк);
- «когорта win vs текущая сделка»;
- коллизии графа (контакт × две сделки × …).

Формально это не робот и не штатный отчёт, но для покупателя — **одна и та же ерунда**: «ещё один радар аномалий».  
Почасовой таймер **выключен**. Новые идеи — только по запросу, штучно, с новым конвейером ниже.

## Новый подход: сначала работа, потом API

### Критерий силы (все три обязательны)

1. **Сцена понедельника** — за 10 секунд видно конкретного человека в конкретный момент («РОП перед планёркой», «менеджер перед созвоном с крупным»).
2. **Платёжный тест** — нетехнический РОП/маркетолог/аккаунт понял бы ценность одной фразой и мог бы заплатить ~подписку Маркета без объяснения «fingerprint / thrashing / P80».
3. **Зазор vs коробка** — явно разобрано, почему не закрывается: штатным экраном, роботом/БП, фильтром, типовым отчётом, чатом, ручным Excel *внутри* привычки команды.

API и placements — **проверка реализуемости в конце**, не генератор сюжета.

### Откуда брать сюжет (источники боли, по приоритету)

1. **Ритуал роли** — что человек делает каждую неделю в B24 и где матерится (планёрка, разбор слитых, передача сделки, онбординг новичка, сверка маркетинг↔продажи).
2. **Дыра Маркета** — категория есть, а «работа» не закрыта (смотреть конкурентов *до* фиксации идеи, не после).
3. **Беклог / `в беклог N`** — дожимать уже выбранное в полный пакет, а не плодить соседей‑близнецов.
4. API‑угол — только если сюжет уже живой и нужно понять, чем опереться в облаке.

### Вне IT‑пузыря (без изменений по сути)

ICP: продажи, маркетинг, аккаунт, поддержка, РОП/комдир.  
Не плодить WIP / оценки часов / теплокарты дедлайнов / скрам‑приёмку.

### Анти‑паттерны «мельницы детекторов» (новый жёсткий блок)

Дисквал, даже если «не робот»:

- серия правок любого поля за N часов → список;
- «источник × ещё одна метрика из истории»;
- path/fingerprint/P80/P90 как **главный** продукт без новой работы в карточке;
- коллизия сущностей ради коллизии («два X на одном Y») без ясного ритуала «что человек сделает за 30 секунд»;
- пятая вариация уже предложенного сюжета (сверка с последними 30 номерами в `PROPOSED.md`).

Старые анти‑паттерны тоже действуют: робот/БП 1:1, дедуп, пустое поле→алерт, нет следующего дела, голый period KPI, фейковый chat handoff, чтение текста чатов.

Отклонённые уроки: **114, 115, 117, 118**, плюс волна **269–273** (штатные отчёты/фильтры), **285/286/288** (робот/БП), поток **274–313** как пример вырождения в радары.

## Конвейер (по запросу «идея» / «ещё», не каждый час)

По умолчанию выпускать **1–2 идеи**, не 5. Пятёрку — только если пользователь явно просит «5» и есть 5 разных *работ*, не 5 детекторов.

1. Выбрать **одну роль** и **один ритуал** (не API‑код).
2. Написать job: «когда … хочу … чтобы …».
3. Разобрать **как сейчас в B24**: экран / робот / БП / отчёт / Excel / чат. Если закрывается терпимо — **стоп**.
4. Сформулировать **клин приложения**: одно действие или один экран, который меняет ритуал.
5. Проверить конкурентов Маркета *и* штатив (коротко, до записи в `PROPOSED`).
6. Только потом приписать API‑угол / placement / MVP.
7. Записать в `PROPOSED.md` + ротацию **ритуалов** (не углов A–J).
8. Commit/push по договорённости потока.

## Формат идеи (для чата)

1. Название на русском (без жаргона)
2. Сцена / боль / цена
3. Что делает (1–2 фразы про работу, не про лог)
4. Для кого
5. Эффект
6. MVP
7. Чем НЕ штатный B24 **и** не робот/БП/фильтр/типовой отчёт
8. Как сейчас обходят (1 фраза)
9. Риски, скоринг, `в беклог N`

В файле дополнительно: домен, placement, механика, API как опора.

## Ротация ритуалов (вместо ротации A–J)

Вести в `PROPOSED.md` блок `## Ротация ритуалов`. Не повторять тот же ритуал, пока не сменится роль.

Примеры ритуалов (не чеклист на выпуск):

- планёрка РОПа / прогноз недели;
- подготовка к созвону с крупным;
- передача сделки другому менеджеру;
- разбор слитых для маркетинга (не «ещё отчёт причин»);
- онбординг новичка продаж;
- допродажа / следующий шаг после win;
- согласование оффера маркетинг↔продажи в момент звонка;
- смена ответственности при отпуске (операционка продаж, не IT).

Таблица API‑углов A–J сохраняется как **справочник реализуемости**, не как барабан генерации:

| Код | Угол | Зачем помнить |
|-----|------|----------------|
| A | События | журналы, реакции |
| B | История стадий | пути, откаты |
| C | Связи | deal↔contact↔activity |
| D | Агрегаты | только внутри живого job |
| E | Оргструктура | маршрутизация |
| F | Placements | действие в карточке |
| G | IM‑метаданные | без текста и фейкового handoff |
| H | Чеклисты/время | осторожно, легко уйти в IT |
| I | Дубли | почти всегда запрет |
| J | Товарные строки | состав КП, не «ещё детектор строк» |

## Разнообразие механик

Если просят несколько идей — разные **работы**, не разные детекторы.  
Детектор/радар: **максимум 1** на пачку, лучше 0.

Предпочтительные механики: действие в карточке, мастер ритуала, помощник решения, один экран «собрать смысл для планёрки».

## Хороший зазор

- Меняет **ритуал** (человек делает иначе через 1 минуту в B24)
- Не сводится к уведомлению робота
- Не сводится к фильтру/отчёту «как есть»
- Покупатель объяснит коллеге своими словами без терминов аналитики

## Красные флаги реализации

- Нет внешних интеграций и отраслевых решений
- Нет тяжёлого realtime / сложных ботов в MVP
- Time‑to‑value ≤ 10 минут
- Минимальные права
- MVP ≤ 1–2 недели, 1 killer‑экран
